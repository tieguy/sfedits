# SFBA bots on the platform code base

Date: 2026-08-15. Status: **plan only — nothing here is executed.**
Every push in this plan is a deploy and waits for explicit go.

## What converges

One process already runs two architectures:

| | SFBA account bot | Platform topics (Venezuela et al.) |
|---|---|---|
| Membership | `public/watchlist-500.json`, committed, regenerated by hand (`reassess.js` + `rank.js`) | topic in ToolsDB, rebuilt nightly from Wikidata via `lib/region.js` |
| Curation | top-500 cut of the editorial-inlink ranking | none — the whole region |
| Delivery | account channels: Discord + Mastodon + Bluesky, with collapse windows, threading, facets | Discord webhook subscriptions |
| Renames / new articles | frozen until the next hand regeneration | `title-resolver` + nightly set-diff rebuild |
| Claim watch | `lib/wikidata-claim-watch.js`, hardcoded to the nine counties | none |

They already share: the membership rule (`memberPattern` /
`IS_HERE_PROPERTIES` in `lib/region.js`), the render-once delivery merge in
`sendStatus`, the substantive-edit filter, and the account/topic isolation
gate in `resolveConsumers`.

The end state: **SFBA is a topic.** Its membership comes from the same
resolver as every other region, its list refreshes nightly, and its curated
top-500 cut is a filter on that topic rather than a separate architecture.
The account's channels keep their identity (collapse, threading,
`top500.thebay.wiki`) but read their watchlist from the topic store.

What the platform must grow to get there, in dependency order: multi-anchor
regions (phase 1), a curation filter (phase 2), a topic-backed watchlist
source for the account (phase 3). Phases 4–5 are optional deepenings.

## Phase 0 — measure, change nothing

Resolve the prospective SFBA topic and diff it against what the bot watches
today. No production change; one afternoon.

1. Run `articlesByAdmin` (en) for each of the nine county QIDs
   (`lib/wikidata-claim-watch.js` has the list) plus `Q213205` (San
   Francisco Bay Area — see phase 1 on why it is an anchor for pointer
   properties even though P131 chains do not reach it), union the results.
2. Set-diff against: the ranked universe (`ranking.json`), the published
   `watchlist-2500.json`, and `watchlist-500.json`.
3. Report three lists with counts: only-in-Wikidata (candidates the
   PageAssessments cohort misses), only-in-cohort (tagged articles Wikidata
   membership misses — this sizes the cohort import, decision table below),
   and the top-500 overlap.
4. Record per-anchor query timings; the SF counties are the scale this has
   to be cheap at.

Everything downstream cites these numbers instead of estimates. Exact
replication of the current watchlist is a **non-goal**: the diffs inform
the cohort and anchor decisions and expose scaling fixes — membership is
allowed to change where the new approach is simply better.

## Phase 1 — multi-anchor regions

The SFBA is not an administrative entity: no P131 chain passes through
`Q213205`, so a single-anchor topic cannot express "the nine counties".
Other metro areas will have the same shape.

- Schema (new migration): `topic_regions (topic_id, region_qid, PRIMARY KEY
  (topic_id, region_qid))`. `topics.region_qid` stays as the display/primary
  anchor; extra anchors live in the new table. Topic-identity invariant:
  the dedup hash must cover the **sorted full anchor set** — extend the
  normalized-filters hashing, do not add a second mechanism.
- `lib/rebuild.js`: resolve each anchor with the existing single-region
  path and union by `(wikipedia, title)` — the same dedup `articlesByAdmin`
  already does across properties. Serial per anchor, per Wikimedia
  etiquette and the WDQS chunking lesson.
- Anchor semantics: every anchor contributes through every membership
  property. This is what makes `Q213205` worth listing even without P131
  children — items with `P159`/`P276` pointing at "San Francisco Bay Area"
  itself are members the county anchors can never see.
- `/create` keeps its single-region form; multi-anchor topics are created
  from the admin console. A public multi-region form is out of scope.
- Estimate path: sum of per-anchor histograms, labelled as an over-estimate
  (anchors overlap); the rebuild remains the truth.

## Phase 2 — curation: ranks in the database, top-N as a topic filter

The platform resolves *everything in a region*; the SF product is *the 500
most important*. Decided 2026-08-15: ranks live as **database rows**, not
a published file. Two halves: the platform consumes ranks (2a), and a
deployed job produces them (2b). 2a can ship first, bootstrapped from the
current ranking.

### 2a — consumption

- Migration: `topic_articles.rank INT NULL` (NULL = not yet ranked). The
  full uncut membership stays in the table — the rank is metadata on it,
  so the uncut set remains inspectable by construction.
- Topic filter `top_n`: the watch index and the watchlist feed include
  only articles with `rank <= top_n`. An article whose rank is NULL (new
  member between rank runs) is **excluded from a top-N topic** until a
  rank run scores it — cut means ranked-and-inside, never "unranked so
  let it through".
- `top_n` participates in `filters_hash` (a cut topic and an uncut
  firehose topic over the same anchors are different feeds and can
  coexist).
- Bootstrap: a one-off import writes ranks from the current
  `ranking.json`; the committed `watchlist-500.json` stays only as the
  published artifact the on-wiki proposal cites.

### 2b — production: the ranking joins the deployment

The ranking cannot stay hand-run in the end state — a frozen cut recreates
the frozen-file problem one level up. It also cannot run *nightly*: the
inlink metric reads wikitext from the enwiki dumps, which publish roughly
twice a month. So it becomes a **per-dump `rank` job** on Toolforge:

- Dumps are mounted at `/public/dumps/public/enwiki/`;
  `lib/dump-reader.js` reads multistream there by design. The job detects
  a new complete dump, recomputes editorial inlinks over the topic's uncut
  membership, and updates `topic_articles.rank` in one transaction.
- The nightly rebuild and the rank job stay decoupled: rebuild moves
  membership, rank moves ordering.
- `rank.js` and `lib/dump-reader.js` live on `place-bot-platform-design`;
  they come over the way `reassess.js` did. The API-bound stages the
  ranking depends on (cohort, redirects) must fit inside the anonymous
  200 req/min cap or wait on LUI-94's authentication scope.
- A failed or half-finished rank run must leave the previous ranks in
  place — same refusal rule as the rebuild, enforced by the transaction.
- Hand-run `rank.js` remains the local dev path, and the tier-boundary
  judgment calls (where the top/high/mid cuts fall) stay human decisions
  expressed as job parameters, not something the job invents.

## Phase 3 — the account reads its watchlist from the topic store

The smallest change that retires the two-architecture split, chosen over
"account channels become subscriptions" (phase 4) because it preserves
everything subscribers cannot yet have — collapse windows, Bluesky
threading and facets, Mastodon visibility, the 300-grapheme truncation —
with no delivery-code changes at all.

- `watchlist_source` gains a `topic_id` variant alongside `titles_url`:
  `lib/watchlist-sync.js` fills `account.dynamicWatchlist` from
  `topic_store.getWatchIndex()` restricted to that topic, mapping language
  codes back to the display names the account path keys on. The existing
  fallback chain (in-memory → cache file → empty) and the
  `✓ Watchlist sync` log line stay; LUI-109's failure mode must not get a
  new variant.
- The account/topic isolation gate (`resolveConsumers`, added after the
  2026-08-15 incident) needs **no change**: `isWatched` keeps consulting
  the account's own (now topic-fed) watchlist. Its regression tests must
  stay green untouched — treat any needed edit to them as a design smell.
- `/watchlist-500.json` keeps being served (public artifact, cited by the
  on-wiki proposal) but stops being load-bearing for the bot.
- Cutover order and verification: config commit is a deploy; after restart
  verify `✓ Watchlist sync: ~500 articles from topic <id>` and one live
  edit posting exactly once per channel. Rollback = revert to `titles_url`
  (one commit).

After this phase, the SFBA bot and the Venezuela bot differ only in
delivery shape and curation filter — same membership code, same rebuild,
same store.

## Phase 4 (optional) — account channels as subscriptions

Full convergence: Mastodon/Bluesky become subscription delivery types and
the "account" concept dissolves into "subscriptions with richer renderers".
Prerequisites that make this its own design, not a step here:

- `lib/subscription-delivery.js` is Discord-only by design (URL allowlist
  as SSRF guard — do not invert it when adding platforms).
- Credentials must not live in `delivery_config` rows: the design is a
  credential *reference* (envvar name) resolved at post time, so the DB
  never holds a secret.
- Collapse, threading, facets, per-platform truncation all have to become
  per-delivery-type capabilities of the subscription path.

Nothing before this phase depends on it; it can wait indefinitely.

## Phase 5 (gated) — claim watch on shared membership

`lib/wikidata-claim-watch.js` builds its place/position target sets with
its own per-county queries — the same shapes `memberPattern` now provides.
Converge it (target sets built per topic from the topic's anchors) **only
after the LUI-120 OOM A/B has a verdict**: that module is deliberately the
unchanged variable in the stability comparison. Until then it stays as is.

## Decisions (resolved 2026-08-15, plan review)

| Decision | Resolution |
|---|---|
| PageAssessments cohort | **Import** it as `topic_articles.source='pageassessments'` — the tagged cohort stays a membership source alongside Wikidata. Phase 0's only-in-cohort diff now sizes the import rather than deciding it. |
| Cut artifact home | **Ranks in DB rows + `top_n` topic filter** (phase 2 above). The committed `watchlist-500.json` survives only as the published artifact the on-wiki proposal cites. |
| SFBA anchor set | **9 counties + `Q213205`**. |
| Sequencing vs LUI-169 (placewatch migration) | **Interleave**: phases 0–2 may proceed alongside placewatch pre-work; the phase-3 cutover and the LUI-169 tool cutover never share a window — two simultaneous "why did posting change" variables. |

## Invariants that must survive every phase

- One render per matched edit, no matter how many consumers.
- Topic-only edits never reach account channels except through the
  account's own (topic-fed) watchlist — the `resolveConsumers` gate and its
  incident-reproduction test.
- Serial WDQS queries, anchored per region/property; a timeout is a scope
  error, not a retry loop.
- Schema changes are migration files; topic identity = normalized filters
  hash (now including anchors and cut).
- Nightly rebuild refuses partial results (a quiet bot is worse than a
  stale list).

## Out of scope

The elections bot (LUI-107); OAuth/authenticated API access as a general
capability (LUI-94 — phase 2b only notes its dependency); public
multi-region creation UI; any change to the social-account identities
(that is LUI-169 territory).
